# Шар даних: підключна архітектура бекенду

Консоль спроєктована так, щоб сховище даних не було прив'язане до конкретної платформи
(зокрема до Verdent). Екрани та бізнес-логіка залежать лише від інтерфейсу `DataBackend`,
тому БД/бекенд змінюється будь-коли — у **Налаштування → «Архітектура даних»** — без
переписування коду і без втрати даних.

## Контракт

```ts
// src/lib/backend/types.ts
export type BackendKind = 'local' | 'supabase' | 'rest';

export interface DataBackend {
  readonly kind: BackendKind;
  /** Завантажити збережений стан (null — ще нічого не збережено). */
  load(): Promise<AppState | null>;
  /** Зберегти стан. Помилки не повинні ламати UI. */
  save(state: AppState): Promise<void>;
  /** Перевірка доступності для екрана «Налаштування». */
  health(): Promise<{ ok: boolean; detail: string }>;
}
```

## Як це працює

1. **localStorage завжди лишається офлайн-кешем.** `store.ts` синхронно пише стан у
   `localchats_console_v1` при кожній зміні — застосунок миттєво запускається і працює
   навіть офлайн.
2. При активному віддаленому бекенді кожна зміна **debounce-пушиться** (800 мс) у нього
   через `scheduleRemoteSave()`. Збереження суворо послідовні (ланцюжок промісів):
   повільний запит не може завершитися пізніше наступного й перезаписати свіжіший стан.
3. Після входу `App.tsx` один раз викликає `pullRemoteState()`: віддалений стан має
   пріоритет над локальним кешем, локальні налаштування UI (фільтри, відкритий вид,
   обраний діалог) зберігаються (`mergeRemote`). Якщо під час завантаження відбулися
   локальні правки — злиття пропускається, щоб не перетерти свіжі зміни.
4. Віддалений payload **валідується перед злиттям** (`sanitizeRemote`): масиви
   (`employees`, `channels`, `conversations`, `clicks`), об'єкт `messages`, рядок
   `currentUserId`. Пошкоджені поля відкидаються — помилкова відповідь сервера не зламає
   рендер і не перезапише локальний стан.
5. Перемикання бекенду — миттєве: змінюється конфіг `connections.backend`, наступний
   `save` іде вже в новий адаптер. Дані в попередньому сховищі не видаляються.

## Готові адаптери

### `local` — localStorage (за замовчуванням)
Автономний режим і офлайн-кеш. Нічого не вимагає.

### `supabase` — Supabase (хмара)
Повний стан консолі зберігається як `jsonb` у таблиці `app_state`, по рядку на
користувача, доступ обмежений RLS (`user_id = auth.uid()`). Потрібна активна сесія
Supabase Auth (вхід у застосунок). Помилка upsert (RLS-відмова, мережа, схема)
не ковтається — пробрасується далі. Схема:

```sql
create table if not exists app_state (
  user_id uuid primary key references auth.users(id) on delete cascade,
  data jsonb not null,
  updated_at timestamptz not null default now()
);
```

### `rest` — будь-який власний сервер
Універсальний адаптер для «власної архітектури»: будь-якого бекенду на VPS, serverless,
Enterprise-сервера. Контракт із двох ендпоінтів:

```
GET  {baseUrl}/state   → 200 + JSON стану | 204, якщо стану ще немає
PUT  {baseUrl}/state   → 2xx, тіло запиту = JSON стану
```

Авторизація: `Authorization: Bearer <apiKey>` (ключ налаштовується в UI, необов'язковий).
CORS: сервер має дозволяти origin консолі для `GET/PUT /state`.

Найпростіший приклад сервера на Node (без залежностей):

```js
import { createServer } from 'node:http';
let state = null;
createServer((req, res) => {
  if (req.url === '/state' && req.method === 'GET') {
    if (!state) { res.writeHead(204); return res.end(); }
    res.writeHead(200, { 'Content-Type': 'application/json' });
    return res.end(state);
  }
  if (req.url === '/state' && req.method === 'PUT') {
    let body = '';
    req.on('data', (c) => (body += c));
    req.on('end', () => { state = body; res.writeHead(204); res.end(); });
    return;
  }
  res.writeHead(404).end();
}).listen(8080);
```

## Як додати свій адаптер (наприклад, Firebase / MongoDB / 1С)

1. Створіть `src/lib/backend/myBackend.ts`, реалізуйте інтерфейс `DataBackend`
   (`load` / `save` / `health`).
2. Зареєструйте його в `getBackend()` у `src/lib/backend/index.ts` і додайте варіант
   у `BackendKind` (`types.ts`).
3. Додайте пункт у селект «Архітектура даних» у `src/components/SettingsView.tsx`.
4. Якщо потрібен свій формат/міграція — опишіть схему в `supabase/schema.sql` або в окремій
   міграції; `AppState` змінювати не потрібно.

Жодні компоненти й `store.ts` при цьому не змінюються — у цьому й полягає незалежність
від конкретної архітектури.

## Безпека: зберігання ключів

**Увага:** конфіг з'єднань (`localchats_connections_v1`), включно з REST-ключем `apiKey`,
ключем воркера та даними Zoho, зберігається у `localStorage` **у відкритому вигляді** і
доступний будь-якому XSS-скрипту на сторінці. Для цієї загрозової моделі (однокористувацька
консоль, ключі належать самому користувачеві) це прийнятний компроміс, але враховуйте це:

- не вводьте сюди серверні секрети (service_role, секрети вебхуків) — лише ключі, якими
  користувач легітимно володіє;
- довгостроково можна перенести ключ у `sessionStorage` (стирається при закритті вкладки)
  або тримати тільки в пам'яті з повторним введенням при вході;
- на серверній стороні (воркер, REST-бекенд) секрети мають жити лише в env.

## Планова еволюція (етап 2)

Зараз бекенд зберігає цілісний стан (state-sync). Наступний крок — нормалізована
схема (`conversations`, `messages`, `clicks` — уже описана в `supabase/schema.sql`) з
Realtime-підписками та ingest-вебхуком від воркера. Для цього реалізується другий інтерфейс
(наприклад, `NormalizedBackend`) над тим самим реєстром адаптерів — UI знову не змінюється.
